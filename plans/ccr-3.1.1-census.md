## 2. How ports and hosts are determined in 3.1.1

Two independent servers, two independent mechanisms.

**Management web server** (`lAe`, `$lt`):
- host: `--host` flag, else env `CCR_WEB_HOST`, else `127.0.0.1`.
- port: `--port` flag, else env `CCR_WEB_PORT` (integer 1..65535), else **3458**. On `EADDRINUSE` it scans up to 20 ports forward (`$lt`), then throws. So the bound port can differ from the requested one; `service.json.url` is authoritative.
- token: `CCR_WEB_AUTH_TOKEN` (else random 32 bytes). RPC header `x-ccr-web-auth`, and `?ccr_web_token=` in the URL.
- `--no-gateway` (parsed by `HG`): `startGateway=false`, so `Blt("web startup")` is skipped and the process binds only the web port.

**Gateway (public + core)**, from the app config (SQLite `app_config`, legacy `config.json` fallback), normalised in `Bt()`:
- defaults (`d8`): `HOST 127.0.0.1`, `PORT 3456`, `routerEndpoint http://127.0.0.1:3456`, `gateway{enabled:true, host:127.0.0.1, port:3456, corePort:3457, coreHost:127.0.0.1}`.
- effective values: `PORT = cfg.PORT ?? port-of(routerEndpoint) ?? 3456`; `gateway.host = cfg.gateway.host ?? HOST`; `gateway.port = cfg.gateway.port ?? PORT`; **`gateway.corePort = cfg.gateway.corePort ?? (PORT + 1)`**; `coreHost` is the compile-time constant `b8 = "127.0.0.1"`.
- `saveAppConfig` (`_8`) strips `gateway.coreHost` and `gateway.corePort` before persisting, so on every read `corePort` is re-derived from the top-level **`PORT`**, not from `gateway.port`. Setting only `gateway.port=39466` leaves `corePort=3457`, a LIVE port.
- There is NO env var for gateway or core ports (grep of all `CCR_*` names: none). Runtime host/port for the core child come from `Iot(config, runtimeHost, runtimePort)`, which are derived from the same config (public-gateway mode uses `gateway.host/port`, otherwise `coreHost/corePort`).
- A start with zero providers and `gateway.enabled=true` throws `Qd` ("No available models. Configure at least one provider with a model...") BEFORE any `listen` (`if(d&&!Ac(t))throw new Error(Qd)` precedes `c&&await this.listen(t)`), so a zero-provider start binds no PUBLIC gateway port even without `--no-gateway`. This is verified by reading the public-listen path only; the core-child listen path was not separately verified, so it is not claimed. Stage 1 still passes `--no-gateway` (defence in depth: one less thing that can bind 3456/3457).
- Before starting the core child it health-probes the core endpoint (`PL`) and refuses if something already answers ("Core gateway endpoint is already in use"), a safety net while the live gateway is up but not a control.

Rule for stage 2 (not now): the sandbox config must set **`PORT`, `gateway.port` and `routerEndpoint`** to the trial values (39466 / 39466 / `http://127.0.0.1:39466`, giving corePort 39467), and this is re-read and asserted after save, never assumed.

## 5. Headless start mode

There is no GUI/tray in `dist/main/cli.js`. Commands: `start` (detached daemon, default), `ui` (start + open browser), `serve`/`web` (foreground; `--daemon-child` makes it write `service.json` and behave as the managed service), `stop`, plus `<profile> [cli|app]`.
- `start` re-spawns `node cli.js serve --daemon-child ...` **detached with `stdio:"ignore"`** and a `service-start.lock`; harder to own and to tear down.
- **Chosen for the trial:** the harness spawns `node <sandbox cli.js> serve --daemon-child --no-open --no-gateway --host 127.0.0.1 --port 39468` itself: one foreground child pid we own, its stdout/stderr go to `run\daemon.*.log`, `service.json` is still written into the sandbox CONFIGDIR (needed for proof checks 1 and 4). A graceful SIGTERM lets CCR remove `service.json` (`mk`), but the harness stops the daemon with `taskkill /F`, which NEVER runs that handler: `service.json` can therefore be stale after a harness stop (a dead pid that may later be recycled). Teardown does not trust it: every pid is checked against the live process table (process Name `node.exe`; the quotes-aware tokenised command line has argv[1] equal to the sandbox `cli.js` and a whole-argument `--daemon-child`, so a wrapper quoting both strings or `--daemon-child-x` does not verify; creation time not older than `startedAt` minus a margin) before any kill, and sandbox daemons are also found by that same test when `service.json` is missing or torn (the creation-time gate applies there too when `startedAt` parses; otherwise teardown says the start time was not checked).
- `ccr start` (the PATH binary) is never used; the global 3.0.22 is never invoked.

## 9. GATE G2 brief: exactly what the first start would do

G2 is the first start of the sandbox management server, with **zero providers and no gateway**. Nothing below has been run.

**Command** (needs the flag `--g2-approved`, otherwise it refuses): `node harness/trial31/start31.mjs --g2-approved` (add `--dry` to run only the preflight and print the spec without starting anything).

**Preflight (all must pass or nothing launches):**
1. Sandbox router is exactly 3.1.1 and ai-gateway >= 1.0.21 (zero-padded numeric compare: `1.0` is not `>= 1.0.21`).
2. No `config.sqlite` in the sandbox (it is a first start, no providers can exist).
3. No listener on any port 39456-39489; live-port owners (3456/3457/3458/4517) recorded, never touched.
4. No live process from the old 3.0.22 `harness\scratch` tree: the pid recorded there counts only if the process table shows it IS a ccr daemon (a recycled pid is ignored). The current HKCU PATH must not already carry a sandbox segment, and no earlier restore kit (`backup\hkcu-path.json`) may exist; it is never overwritten.
5. Creates the sandbox dirs and applies an owner-only ACL to the sandbox root: GRANT the current user by SID first, THEN remove inheritance, verified by readback (exactly one entry, ours, full control, nothing inherited). The prebuilt `better_sqlite3.node` is copied from the real 3.0.22 install after checking both are 12.11.1 (read of a real file, write inside the sandbox): temp name, sha256 compare with the source, atomic rename; an existing copy is re-verified by hash. Then a PRE-LAUNCH CANARY runs a node child with the exact launch env and must prove the preload is honoured (guard flag set and an outside write blocked) or nothing launches; stale `violations.log` and `guard-loaded.log` are rotated to `*.prev-<ts>`. Under `--dry` steps 5 and 7 and the launch do not happen; step 6 (`assertLaunchSpec`) DOES run and its spec is printed; the real `settings.json` is read (count and sha256 only) in the preflight, before anything is created, and an unreadable file is a preflight refusal. After the read-only preflight only "would ..." lines are printed.
